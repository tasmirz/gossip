# Gossip dashboard redesign and local access plan

## What broke

The dashboard inherited the network sign-in model. It maps each browser session to a set of project tokens. Registry mode originally filled that map from saved credentials, so an existing local project could be invisible on a fresh browser if its token was never imported. At the same time, the overview showed almost every panel even though the frontend only loaded data for the active view. This produced empty workspaces, a narrow chat timeline, cramped access forms, and controls that offered credential import as the way into a local project.

The current worktree has an unfinished change that enumerates owners on loopback and passes a synthetic token through shared authorization. Treat it as a prototype. It has not been verified against the remote boundary, existing sessions, or recovery export.

## 1. Separate local and network access

- **Local dashboard.** Opening the local dashboard lists projects in the device’s coordinator database. A fresh browser can open an existing project by URL or choose it from the project list. No project token, credential file, import step, certificate, or per-project login appears in this flow. Creating a project opens Chat immediately.
- **Local authority.** Give the local dashboard an explicit device-owner authorization path, enabled only by the local dashboard constructor and only for direct loopback requests with an allowed Host. The authorization layer should accept a typed server-derived identity and resolve it to the active local owner for the selected project. Keep the existing permission and audit checks downstream. Never accept an owner ID or local-mode flag supplied by the browser. Define the owner mapping when projects are created and use the existing active owner for legacy projects with one owner. If a legacy project has no active owner or ambiguous ownership, expose a local administrative repair state with an explicit selection. Do not pick an arbitrary owner by ID.
- **Browser boundary.** Keep origin checks on writes, add cross-site request and framing protections where needed, and never trust forwarded addresses. Loopback is a machine boundary, not proof of a particular OS user. For a shared machine or an environment with local proxies, bind the privileged backend to a private OS user endpoint and use an OS-mediated browser launch or one device-level session. Do not expose unrestricted owner authority to other local accounts. Keep the loopback dashboard off LAN listeners and FRP.
- **Network boundary.** LAN and FRP peers authenticate with a project membership credential and an active client certificate grant for that project. The peer listener must never use the local owner path or serve the dashboard. A joined project on the recipient’s dashboard uses its saved remote connection in the background. Route it by home and project identity so a remote project cannot acquire local owner authority, even if IDs collide.
- **MCP boundary.** Keep agent profiles and their permissions distinct from the human dashboard. An agent cannot obtain human owner access by omitting its project credential or choosing the dashboard profile. The device registry can retain agent and remote credentials privately. The browser should never receive those credentials through normal project browsing.
- **Migration.** Replace the unfinished synthetic-token branch in shared authentication with the explicit local authorization path. Preserve existing owner IDs, project history, and remote grants. Retain legacy import as a secondary connection or recovery action. Export only a real saved credential after explicit owner action. When an old credential is unavailable, offer issuance of a new scoped credential through Access rather than returning a placeholder or silently rotating existing tokens.

## 2. Rebuild the dashboard around routes

Use a persistent project switcher and dedicated views. Put one primary action on each screen. Open the most recent local project in Chat, or show a project list if no project is selected. Preserve existing project links and keep the selected view in the URL.

| View | Design and behavior |
|---|---|
| **Projects** | List local projects and joined projects with connection status. Make **Add project** the primary action. Offer **Local checkout** and **Join LAN or remote project**. Preview the local Git folder and open an existing match before offering creation. Keep credential import behind the remote or recovery flow. |
| **Chat** | Use the channel-and-DM layout here. Give the timeline the full remaining width and its own scroll area. Keep the composer visible. At narrow widths show the conversation picker and timeline as separate panes with a Back action. Preserve drafts and scroll by conversation. Use server-filtered history, older-message loading, and incremental refresh. |
| **Plans** | Treat each plan as an independent project workstream. A project may keep several plans at once, including completed plans that are not versions of a newer plan. Show all plans together in one Plans view; select a plan, then select and compare revisions only within that plan. Keep status (active, done, archived), task list, walkthrough, variants, and progress scoped to the selected plan. A new plan creates a separate workstream; publishing a revision updates only its existing plan and carries its tasks forward. Keep project goals, stories, invariants, and decisions in project context, separate from plans. Render Markdown safely with visible headings and code. Preserve drafts on revision conflicts and avoid nested scrolling inside a small overview card. |
| **To-dos** | Show **My assigned tasks**, **Project to-dos**, and the agent’s personal checklist as distinct lists. Give filters readable labels and room to wrap. Keep quick creation and task detail available without leaving the list. |
| **Agents** | Show the agent tree and profiles. Keep names, roles, declared skills, personal to-dos, and presence visible. Provide a direct route to DM or call an agent. Use explicit parent links and never infer permissions from hierarchy. |
| **Search** | Keep search reachable from every project view. Separate authorized text results and Graphify inspection. Report unavailable or stale indexing clearly. Keep private messages restricted to participants. |
| **Settings** | Separate Access, Connections, Workspaces, and History. Move certificate grants and pairing into **Access → LAN and remote**. Keep recovery export there. Show reservations in Workspaces with holder and expiry. Use a readable single-column form when space is limited. |

In chat, show **You** only for the signed-in principal’s own messages. If Antigravity is signed in, its messages say **You** and other viewers see **Antigravity**. Resolve this using principal IDs. Leave historical labels and attribution intact where the data cannot verify a match. Keep the selected DM recipient visible in the composer. Preserve the task and plan actions from chat, including explicit confirmation before copying a DM into shared content.

The overview, if retained, is a short summary with links to these views. Do not mount access forms, chat, and workspaces side by side on that screen. Use one route loader per view, discard stale responses after project switches, and distinguish loading, empty, and error states. Load inbox and connection status where users can act on them.

## 3. Implement and verify

1. Land the local/network authorization split and migration first. Test an existing project with an empty registry and no cookies, then test new project setup, a direct project link, project switching, refresh, and recovery export. Confirm cross-origin writes, forged local identity, spoofed forwarding headers, direct LAN access, and peer access without the project’s credential and certificate fail. Verify an authenticated peer sees only its granted projects.
2. Replace the page shell and route loaders. Build Chat, Plans, To-dos, Agents, and Settings as dedicated layouts using existing APIs wherever they fit. Keep the rest of the redesign scope in the original plan. Mark unavailable features honestly instead of showing empty panels that look broken.
3. Verify in a browser at desktop and narrow widths, including 1100 px, 768 px, and 390 px. Test long messages, labels, and IDs, keyboard navigation, switching projects during a request, first launch, no projects, and errors. Check that chat never collapses to a word-wide column, filters remain readable, and the local flow never asks for a project credential.
4. Preserve the inbox, wake, guarded editing, and autostart work from the attached follow-up plan. Run its targeted tests and the Go suite. Verify native installers on their actual platforms. For development on this machine, use `bash scripts/build.sh --restart` after the checks pass and confirm the running dashboard PID matches the service manager.
