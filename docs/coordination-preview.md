# Local coordination preview

The coordination preview provides a separate SQLite-backed project store and MCP tool profile. It is an implementation increment toward the [redesign](gossip-redesign-plan.md); its historical archive does not replace or cut over the legacy JSON stores. The default MCP client configurations use this project-scoped profile and a private credential. The legacy JSON MCP CLI transport is retired because it has no project membership boundary. The editor installer defers MCP registration until a project-scoped credential exists.

Run `gossip coord-migrate --legacy-dir /path/to/.local/gossip` for a read-only preflight. It reports file hashes and record counts, malformed messages, invalid task and milestone dependencies, SOP artifact inventories and missing files, and legacy identity or role data that requires review. It flags unsafe artifact paths and explicitly excludes vault secrets. Only audit reports with `ready_for_import: true` have no structural errors; warnings still require an explicit mapping decision.

After reviewing the audit, import supported records into an existing SQLite project with its private owner credential:

```sh
gossip coord-migrate --legacy-dir /path/to/.local/gossip --db /private/path/coord.db --credential-file /private/path/owner.json --apply
```

If the audit reports warnings, resolve them or explicitly accept their historical treatment with `--accept-warnings`. The importer takes the legacy store lock, rechecks source hashes, and aborts if source files changed. It imports goals, agents as unverified historical actors, tasks, messages, SOP workflows/artifacts, and artifact files into a project-scoped read-only history archive. Old roles, assignments, task statuses, and identities do not become permissions, active claims, or verified acceptances. Vault data, guardrails, graph indexes, and other legacy stores are excluded. Repeating the same source import is idempotent. This is a history import only; the legacy service remains writable and no compatibility cutover or rollback workflow is implemented yet. The importer creates or uses the legacy `.lock` coordination file while it runs.

The local dashboard distinguishes **Connect project credential** from local project setup. Connecting requires the private JSON created for the same coordination database used by `coord-ui` (use matching `--db` arguments); a legacy `.local/gossip` directory is not a coordination credential. To start from an existing checkout, choose **Create local project** (or **Set up a local project** from a project-required view), paste the checkout's full path into **Connect a code folder**, and submit. The project name defaults to its inferred Git remote name or folder name. The dashboard creates the coordination project, repository, and first workspace together and downloads the owner credential once; restrict the downloaded file to mode `0600` before use. This local bootstrap is available only from the loopback dashboard.

Create a project and enroll a worker on the same machine:

```sh
gossip coord-init --name "My project" --owner "Coordinator" --credential-file /private/path/owner.json
gossip coord-add --owner-credential /private/path/owner.json --name "Worker" --role worker --credential-file /private/path/worker.json
```

Choose private paths whose parent directories already exist. A 0600 credential file is durably written before project creation or enrollment, so a lost response does not lose the only copy of the credential. If a command reports that the credential was retained, retry the same command with `--resume` and the same names and role; the service safely deduplicates the prepared identity. Keep the file private and do not edit it. Use `--db /private/path/coord.db` consistently for local commands to override the per-user default database. The database must be on a local filesystem; do not share it across machines.

Project access is granted one project at a time: choose the project, enroll the person or agent as a member, and deliver that project's credential. A principal with access to several projects needs a separate credential for each project; access never carries over from one project to another. Revoking a member removes that project access immediately. Every network client, including a client on the LAN, must present that project's member credential. When the connection uses the TLS coordination endpoint (whether reached directly on a LAN or through FRP), the client must also present a CA-verified certificate with a grant for that same project. A local Unix-socket client uses its project credential and the private socket boundary; it does not use the network TLS certificate gate.

An owner can manage access and enroll members over the verified home connection from an administration machine. First grant that machine's client certificate to the project through a trusted local path. Then use `gossip coord-access --remote https://host:8443 --tls-ca /private/server-ca.crt --tls-cert /private/admin-client.crt --tls-key /private/admin-client.key --owner-credential /private/path/owner.json --action grant --certificate /private/worker-client.crt`, or use `gossip coord-add` with the same remote/TLS options and `--name`, `--role`, and `--credential-file` to enroll a project principal. The home requires both the certificate's project grant and the owner's project credential. The new member credential is generated and saved privately on the administration machine; deliver it to the member through a separate secure channel. Project creation over the network requires the separately configured create-only bootstrap key plus a CA-verified client certificate; all later project operations require the new project's owner or member credential and its project certificate grant.

Configure each coding-agent host to launch `gossip coord-mcp --credential-file /private/path/<credential>.json`, adding the same `--db` argument if used above. Separate credentials identify the owner and each worker. Each adapter binds the project and credential at startup; the model does not pass credentials as tool arguments. The adapter reports its own MCP, Git observation, lease-renewal, and optional outbox capabilities with source `adapter`. `coord-mcp --host-capabilities notification,interrupt` can record configured host capabilities; these appear as `host_reported` metadata and are not verification or permissions. The Agents panel labels their source and continues to show execution as unknown.

For MCP-driven project creation, generate a private key with `gossip coord-bootstrap-key --key-file /private/path/bootstrap.key` on the remote home, then provision it to the authorized MCP host through a secure channel. Start the home with `coord-serve --bootstrap-api-key-file /private/path/bootstrap.key`. For a local database, use `gossip coord-bootstrap-key --db /private/path/coord.db --key-file /private/path/bootstrap.key`; this stores only the SHA-256 digest in that database, and the create-only MCP server verifies the supplied key before project creation. Use the same database with `coord-mcp-bootstrap`, or the private socket for a daemon using that database. Configure a separate stdio server on the MCP host:

```json
{
  "mcpServers": {
    "gossip-project-bootstrap": {
      "command": "/usr/local/bin/gossip",
      "args": ["coord-mcp-bootstrap", "--remote", "https://home.example:8443", "--tls-ca", "/private/path/server-ca.crt", "--tls-cert", "/private/path/bootstrap-client.crt", "--tls-key", "/private/path/bootstrap-client.key", "--bootstrap-api-key-file", "/private/path/bootstrap.key", "--credential-dir", "/private/path/gossip/credentials"]
    }
  }
}
```

This create-only MCP server exposes `gossip_create_project`, which inspects a local Git folder, infers repository and workspace metadata, and saves the new owner credential in a private mode-0600 file before attempting creation. Supply a stable `request_id` and reuse it after an uncertain result; the prepared credential is durable and retries are idempotent. The tool never returns its token to the model. Remote bootstrap requires both the CA-verified TLS client certificate and the bootstrap API key; the key authorizes project creation only and does not grant access to existing projects. The creating certificate is granted to the new project atomically with its owner principal and initial workspace, so that host can immediately start the regular project-scoped `coord-mcp --remote` server using the saved owner credential. Owners can revoke that certificate grant independently. For local creation, the database's stored key digest is checked for every create request; an unconfigured or incorrect key is rejected. The checked-in client examples include this as a separate `gossip-project-bootstrap` server and use only a private key-file path placeholder; keep the key outside the repository and replace the example path in the MCP client's trusted configuration.

HTTPS requests require an explicitly allowed Host, a verified client certificate, and a current project certificate grant. Register additional checkouts in Workspaces. The browser receives an HttpOnly local session cookie; the service keeps each connected project's credential in memory. The overview rechecks each project credential and, remotely, its certificate grant before returning project metadata. The conversation status shows the result of the latest complete project refresh; when disconnected, the dashboard keeps the last successful data visible and marks it offline or degraded. If the service restarts while a tab is open, the UI clears stale project data and returns to credential reconnection instead of leaving an unauthorized project view on screen. The sidebar's **Find by Git remote** searches only those connected projects. An owner registers hints from the Workspaces view or with `gossip_workspace` operation `add_remote_hint`; normalized hints omit URL credentials and query data. A match selects a project suggestion only; it never adds membership. Multiple matches remain explicit choices. Signing out or restarting the dashboard clears the session. The Agents and access panel names the selected project and stable project ID directly above membership, permission, and certificate controls; all changes there apply only to that project. It shows adapter process presence from authenticated heartbeats, which start only after a successful MCP initialization and repeat every 15 seconds while the adapter runs; presence expires after 45 seconds without a heartbeat. The Agents view displays the MCP initialization client name and version as self-reported recognition labels, never as identity proof or permissions. It does not claim the agent is currently working or able to accept work. Presence separately displays adapter capabilities and optional unverified `host_reported` capability labels; neither changes project permissions nor proves a managed process is running.

Dashboard API errors distinguish authentication from permission denial. A missing, disconnected, or revoked project credential returns HTTP 401 with reconnect guidance. A valid project session that lacks the required role/capability, or a client certificate not granted to the selected project, returns HTTP 403 with an authorization explanation. An empty project list means this dashboard database has no projects connected to the browser. Start a new project from **Connect a project** and a local Git folder, or connect an existing project with its owner or member credential.

Reports can include fenced `mermaid` sequence, class, state, or flow diagrams. The local UI renders them inside a sandboxed iframe with no network access; the original report text remains visible. The embedded Mermaid 12.3.0 distribution is accompanied by its license in `pkg/coord/ui/MERMAID-LICENSE.txt`.

Use the adapter's tool schemas for arguments:

1. Owner calls `gossip_plan` with operation `publish`, `expected_revision: 0`, and the plan text.
2. Owner calls `gossip_task` with operation `create`, a stable unique `request_id`, the plan revision, `kind: research`, task scope, questions, requested formats, coverage, and review mode. Reuse the same ID and exact payload if the response is lost; the project/principal-scoped record returns the existing task and rejects a changed payload. Use `gossip_agents` to list enrolled principals and `gossip_task` with operation `assign` and `assigned_to` to direct unclaimed work to one worker. An empty assignee makes it available to eligible peers. During planning, optionally set `required_role` to an active owner-assigned project or task role; assignment and claim both reject agents without that role, and claim rechecks it so expiry or revocation takes effect. `required_capabilities` can additionally require a bounded set of supported features; claim succeeds only if one recent authenticated agent session reports every requirement. Capability labels describe adapter support or unverified host configuration, not proof of active execution. The dashboard exposes role presets, role assignment, required-role selection, and required-capability selection. Use operation `search` with optional status, kind, assignee, text query and cursor to browse project tasks in pages. Text search is case-insensitive across task IDs, titles and descriptions, with a 256-character limit. The dashboard exposes the same filters; project, status, type, assignee and query are encoded in the URL for sharing, and each browser can save up to 20 named filters per project. Saved views stay in that browser's local storage and are not shared with project members.
3. Worker reads and acknowledges the current plan with `gossip_plan`, then calls `gossip_task` with operation `claim`, performs the work, and calls `gossip_submit` with the attempt number, source baseline and report. `gossip_workspace` can register a repository and workspace and attach a workspace snapshot to a claim. The attempt records the workspace commit and dirty flag; reports and saved candidates must name that recorded commit when available. The commit is the base revision, while dirty file contents are not snapshotted and remain an explicit verification limitation. Task details expose the attempt owner, recorded commit and dirty-at-claim flag to authorized project members so reviewers can check the source context. An owner can add or remove sanitized repository URL hints; they support project suggestions and never grant membership. `inspect_git` observes the adapter host's checkout, including branch, head, dirty status, and sanitized remote hints. `recognize_git` returns repositories matched by those hints within the adapter's bound project, without registering a workspace. `register_git` records the observation against an explicitly selected repository. The local common-directory fingerprint is a matching hint, not a project identity. Observations can become stale as files change.

When an MCP claim includes `workspace_id`, the adapter refreshes the caller-owned Git workspace on its own host and atomically records the observation with the claim. The registered path must be the Git root. Use `refresh_git: false` only when intentionally using a non-Git or manually maintained workspace. The local dashboard currently claims using the stored observation. Git inspection is a point-in-time observation and does not prevent later workspace changes.
4. Owner or a different reviewer reads the report with `gossip_read`, then calls `gossip_review` with the report ID and digest. A dependent task becomes ready after all prerequisites are accepted.
5. Agents can exchange project or direct messages with `gossip_send`; `gossip_read` with operation `messages` reads visible messages after a sequence cursor. `gossip_sync` reads project event metadata. Its `wait` operation can hold an MCP call open for up to 25 seconds for visible events after a cursor; it returns immediately when events arrive and never acknowledges them. Orchestrators can wait after delegating work instead of repeatedly polling. Its `refresh_cache` operation explicitly refreshes a point-in-time local cache of the current plan, the first page of up to 200 tasks, task counts, and up to 200 events after the cached event cursor. The home reads this bounded snapshot and event page in one database transaction; the local cache commits the data and next visible-event cursor together. If the local cursor is ahead of the home event watermark, the result flags a reset and replaces cached project data before continuing from the home snapshot. A later refresh that receives an authorization denial clears received snapshots and events; `clear_cache` does this locally at any time. Pending outbound requests remain queued for inspection and are not retried without authorization. The result reports observation time, snapshot sequence, task pagination, the next event cursor, and whether more events may be available. These snapshots are bounded, local, and non-authoritative; this does not replicate authority or provide a complete offline project replica, so use live reads for current state. Direct-message send and acknowledgment events are visible only to that message's sender and recipient. Certificate access audit events are visible only to owners. Other project members cannot advance a checkpoint using those hidden event sequences.

For a retryable message, supply a unique `request_id` to `gossip_send` and reuse it with the exact same recipient, thread, subject, and body if the result is uncertain. The home node returns the original message without creating a second event; changing the payload with the same ID is rejected. IDs are scoped to the project and sender. This is not an offline outbox: the sender must retain the ID and retry, and an acknowledgment still requires an explicit recipient action.

`gossip_submit` uses a stable task-attempt idempotency key by default; callers may supply `request_id` and must reuse it only with the identical payload. If a remote home is temporarily unavailable and this adapter has an outbox, the report is durably queued and the active lease continues renewing until delivery succeeds. Use `report_outbox` to inspect queue metadata, `retry_report` for a permanently rejected entry after fixing its cause, `discard_report` to remove a failed entry, and `prune_reports` to remove delivered metadata and its local body. Queue listings never return report bodies. A retry after home commit returns the original report instead of duplicating the task transition or event. `gossip_submit` returns report metadata and digest without echoing the submitted body. `gossip_read` returns an excerpt of at most 2,048 Unicode code points by default. Pass `offset` and `max_chars` (up to 16,384) to retrieve further excerpts; continue with `next_offset` until it is absent. The dashboard's report view still fetches the complete report for display.

Plan changes invalidate existing non-cancelled work for explicit reconciliation. A claim has a renewable lease and a fencing number; a stale or revoked attempt cannot submit its result. Reports and events are stored transactionally with the corresponding task change. A review records acceptance of the exact report digest, not verification of the report's claims.

For remote access, configure a TLS server certificate, trusted client CA, client certificate/key, and server CA through your secure certificate-management process. Grant a certificate to the project using its owner credential: `gossip coord-access --db /private/path/coord.db --credential-file /private/path/owner.json --action grant --certificate /private/alice.crt`. Add `--expires-in 24h` for time-limited access; omitting it grants indefinitely. The dashboard and `gossip_access` also accept an optional expiry. Expired grants remain listed for owner review or renewal but fail authorization on the next request. `coord-access --action list` lists grants and `--action revoke --certificate ...` removes one; these owner actions can also run through the private Unix socket with `--socket`. Start the home node with `gossip coord-serve --db /private/path/coord.db --tls-cert /private/server.crt --tls-key /private/server.key --client-ca /private/client-ca.crt`. The CA validates the certificate chain; each request also checks the certificate fingerprint's project grant in SQLite and the bearer credential's project membership; each operation then checks its project action grants. Grant and revoke changes apply on the next request without restarting either service. The endpoint listens on `127.0.0.1:8443` by default. An explicit `--listen` address can expose the TLS endpoint on a LAN; a TCP FRP tunnel can forward to the loopback listener. On the remote machine launch `gossip coord-mcp --remote https://host:port --tls-ca /private/server-ca.crt --tls-cert /private/client.crt --tls-key /private/client.key --credential-file /private/worker.json`. The server certificate must match the host, or set `--tls-server-name` to a name on the certificate. Provision project credentials and client private keys through an independent secure channel.

Remote access is **disabled by default**, including for databases upgraded from earlier versions. Enable it explicitly on the home host with `gossip coord-remote --action enable --db /private/path/coord.db`; when `coord-daemon` holds the database open, use `--socket /private/path/coord.sock`. `status` reports the switch and `disable` blocks remote TLS RPC and remote HTTPS dashboard requests immediately, including requests arriving through FRP. Network clients cannot change this switch. Loopback HTTP dashboard access remains available when remote access is disabled.

The local dashboard Settings view also shows the switch state. It is read-only; change the setting with the local CLI or private Unix socket, so an unauthenticated localhost HTTP request cannot toggle the host-wide boundary.

Remote `coord-mcp` creates a private per-credential local outbox by default; pass `--outbox /private/path/worker-outbox.db` to choose another path. This enables durable message and review handoffs, cached sync, and the stable project-scoped replica ID used for owner-visible receipts.

For a short-lived certificate pairing invitation, the owner can use the dashboard Agents panel or run `gossip coord-pair --action create --db /private/path/coord.db --owner-credential /private/owner.json --invite-file /private/invite.json --expires-in 10m --certificate /private/client.crt`. The optional certificate binds the invitation to that fingerprint before delivery; without it, the first CA-verified client holding the invitation can redeem it. The invitation file is prepared and synced before enrollment, so `--resume` retries the same invitation after an uncertain response. Deliver the file privately. On the client, set its mode to 0600 and run `gossip coord-pair --action redeem --remote https://host:port --tls-ca /private/server-ca.crt --tls-cert /private/client.crt --tls-key /private/client.key --invite-file /private/invite.json`. Redemption binds one certificate fingerprint to the project and may be retried by that same certificate after a lost response. It cannot restore a grant the owner later revokes. An owner can use `coord-pair --action list` and `coord-pair --action revoke --id <invitation-id>` before redemption. Pairing does not enroll a principal or deliver a project credential; use `coord-add` or the dashboard invitation separately.

To generate the home node's FRP TCP config, run `gossip coord-frp --server frps.example --server-port 7000 --token <frp-token> --remote-port 18443 --config-file /private/path/coord-frpc.toml`, then start `frpc -c /private/path/coord-frpc.toml`. The command writes a new config file with mode 0600 and refuses to overwrite an existing file. The config forwards TCP to `127.0.0.1:8443`; the coordination server's HTTPS mutual TLS stays end-to-end through FRP. Open the selected `--remote-port` on the FRP server and connect clients to `https://frps.example:18443`; set `--tls-server-name` when the coordination server certificate names a different host.

Use the [two-host acceptance runbook](two-host-acceptance.md) to verify membership and certificate isolation, reconnect, restart, revocation, and the review handoff between separate physical machines. The completed run record is a release gate; same-host FRP and container tests do not replace it. Every remote connection requires a CA-verified client certificate with a current database grant for the requested project and a project-scoped credential. The certificate project grant and project role are both checked; the certificate alone grants no project membership. An owner may enroll a member and grant its certificate to the selected project atomically. Access to any additional project requires a separate project credential and certificate grant. The remote adapter validates the server certificate and refuses redirects. Mutations are not retried automatically. Task creation, messages, candidate saves, integration records, and review requests have stable request IDs for safe explicit retry; reuse the same ID and payload after an uncertain outcome. Other mutations can still have an unknown outcome after a connection loss, so inspect state before retrying them. The TLS endpoint is an online connection to one home database, not offline federation or replication. The FRP integration test exercises TCP forwarding, client restart, a one-project remote invite, project-scoped access, and immediate certificate-grant revocation through the tunnel on one host; it passed with FRP 0.72.0. Run it with `GOSSIP_TEST_FRPS=/path/to/frps GOSSIP_TEST_FRPC=/path/to/frpc go test ./pkg/coord -run '^TestRemoteMutualTLSResearchHandoff$' -count=1`. This does not establish multi-machine deployment or offline delivery.

Each remote MCP adapter's private outbox stores a stable random replica ID alongside its project/home/credential binding; it does not store the credential itself. An authenticated `gossip_sync` records a receipt on the home node bound to that project, principal, and the currently granted client certificate. The receipt records the sync cursor and snapshot watermark and is visible to project owners in **Agents**. Reusing the ID under another principal or certificate is rejected. A receipt is historical sync metadata, not a liveness signal or access grant; the project credential and certificate grant are checked again on every request.

The preview has a scoped remote outbox for messages, candidate reports, review requests, and integration records, and a read-only legacy history import. It does not yet implement full replicated federation, model wake-up, automatic agent launching, actual provider spending enforcement, or per-device event delivery acknowledgments. Local OS users who can read another agent's credential or database are inside its trust boundary. Report token targets and requested formats are advisory. The legacy dashboard still uses its existing JSON store, so its tasks and messages do not appear in this preview. Use the project-scoped coordination service for multi-agent access control. Legacy MCP no longer exposes `gossip_remote_query`/`gsp_remote_query`, which accepted model-supplied endpoints and Basic Auth credentials, or `gossip_introduce_remote_peer`/`gossip_handshake`/`gsp_introduce_peer`, which accepted model-supplied remote IDs, roles, and endpoints. The `coord-mcp` process automatically renews leases for successful claims it makes, until submission, blocking, cancellation, ownership loss, or process shutdown. Set `auto_renew: false` on a claim to use a fixed lease. Renewal continues while the adapter is alive, even if its host agent is idle; it is not proof of active work. Network failures can still let a lease expire, and the server's fencing rules remain authoritative. Dashboard claims and callers using the standalone `MCPServer` constructor do not receive automatic renewal.

`gossip_sync` supports a durable checkpoint per project credential: call `checkpoint`, read events after its sequence, process them, then call `acknowledge` with the last processed sequence. Acknowledgments are monotonic and retryable, and must name an existing event in that project. Reading does not acknowledge processing. All sessions sharing a credential share its checkpoint, so use separate credentials for independent consumers. With an outbox configured, successful event reads are also kept in a bounded local cache; `operation: cached` reads previously observed events while disconnected and labels them as potentially stale. Offline cache reads do not acknowledge the home checkpoint or prove that an agent acted on an event.

When an attempt has lost authority, its author can use `gossip_submit` with operation `save_candidate`, the original task ID and attempt, baseline, and body. Candidates are stored separately and do not submit or complete the task; `list_candidates` returns metadata and `get_candidate` retrieves the full body. The activity view links to recent candidates. This direct operation requires an online home node; see the queued candidate operation below for disconnected work.

Remote `coord-mcp` can optionally persist outbound chat in a private local SQLite file using `--outbox /private/path/outbox.db`. With that option, call `gossip_send` with `operation: enqueue`; the response says pending and the adapter retries delivery while running. Retries use bounded exponential backoff with deterministic jitter; an entry in backoff does not block later eligible chat or candidate entries. `operation: outbox` lists pending, delivered and failed entries without their bodies; `retry` requeues a failed entry by request ID, and `prune_delivered` frees delivered entries. The queue holds at most 1,000 entries and is bound to the configured home, project and credential; protect the file because it contains message text and previously observed event data. Pending entries survive process restarts. Delivery confirms the home committed the message, not that a recipient read it. This is scoped caching and outbound delivery, not full replica synchronization or peer pairing.

When a remote adapter has an outbox configured, successful `gossip_plan` `read`, `gossip_task` `list`, and `gossip_sync` `events` calls also save the returned data locally. While disconnected, use operation `cached` on those tools to read snapshots or cached event pages with observation time/cursor metadata. `gossip_sync` `refresh_cache` walks all task pages by stable keyset cursor, up to 10,000 tasks and 8 MiB; an ordinary `gossip_task` `list` caches only that requested page. Task pages are read during one refresh rather than one long database transaction, so concurrent changes may be observed at different times; refresh again to catch newer state. A cache refresh drains event pages up to 10,000 events or 64 MiB of new events; `events_may_continue` means a local bound stopped the drain, and the returned cursor allows the next refresh to continue. The event cache retains at most 10,000 events and 64 MiB observed by that project credential, whichever limit is reached first. These are not a complete project replica. Cached data is explicitly stale-capable and does not establish current authorization or lease ownership. A stable home identity is stored in the coordination database, so restarting the service preserves the replica cursor; a changed home identity or regressed event sequence requires a snapshot and event-cache reset. Revocation clears a replica cache when its next live sync is denied, but a disconnected replica cannot learn about revocation until it reconnects. Live reads and all authoritative changes still require the home node. Protect the database and its SQLite sidecar files as project data.

With a configured remote outbox, `gossip_submit` operation `enqueue_candidate` stores a task ID, attempt, baseline and report locally and returns pending. The adapter retries it as a candidate when the home is reachable; `candidate_outbox` shows status and home candidate ID, `retry_candidate` requeues a rejected entry by request ID, `discard_candidate` removes a permanently failed entry, and `prune_candidates` removes delivered entries. Pending entries cannot be discarded while the delivery outcome is uncertain. The home validates that the credential owns the recorded attempt and deduplicates retries. Delivery never submits or accepts the task. The local queue is bounded to 100 entries and 32 MiB of report bodies; protect and back up the outbox accordingly.

Owners can enable a project token reservation envelope through `gossip_budget` or the Settings view. Once enabled, each task needs a positive reservation before claim; allocations are checked transactionally against the project limit. Reservations persist through cancellation and acceptance until an owner explicitly releases them, and cannot be changed while the task is marked running. Set the initial limit only when no tasks are running. These are planning allocations, not hard provider spending limits: connected agents may exceed them. The active worker can submit one immutable, idempotent `gossip_usage` summary per attempt. Settings shows reported token totals and reported costs grouped by currency and labels each source as provider-reported, host-reported, or estimated. These values are self-reported and not provider-verified; missing records mean usage is unavailable, not zero. Each claim holds an additional attempt allocation until an owner explicitly releases the task reservation, including for expired or blocked attempts; a retry fails if this would exceed the envelope. Existing preview databases are upgraded conservatively by holding the current allocation for each recorded attempt on a reserved task, which can put an existing project over its limit until the owner reconciles it.

Owners can assign project-wide or task-scoped work roles through `gossip_roles` or the Agents view. The Gossip-authored coordinator, researcher, implementer, reviewer, verifier and integrator presets are versioned and include duties, expected output, a compact handoff format, and escalation conditions. The Agents form loads this catalog from the selected project's authenticated endpoint, previews each preset, and also accepts custom role names and duties. Applying a preset stores those instructions with the assignment; custom duties and expiry are supported. The revision prevents overwriting a concurrent change, and role changes appear in activity. These are guidance only: the enrolled owner/worker/reviewer grant still determines permissions. Presets are source-informed starting points, not benchmark-proven “best” roles or imported third-party skills; see [role and skill research](role-skill-research.md). The agent must read current duties when it needs them.

During task planning, ask the user to choose a full code review or a Markdown report with UML class and sequence diagrams when the request does not specify a type. Both the dashboard and coordination service require an explicit selection; task creation rejects an omitted review type instead of silently assuming full code review. For `full_code`, the worker should call `gossip_submit` with `operation: capture_diff`, the task and attempt IDs, and a stable `request_id` before requesting review. The adapter reads the recorded commit baseline and captures the current Git worktree diff, including staged, unstaged, and non-ignored untracked files. It only reads the checkout whose Git root matches the current MCP process, disables external diff/text conversion helpers, and limits the artifact to 1 MiB and 1,000 untracked files. When remote delivery is offline and an outbox is configured, capture queues the candidate for retry. The lower-level `save_candidate` operation remains available for manually supplied artifacts; structural diff validation cannot prove that a manually supplied patch includes every intended change. The durable review event pins the candidate ID, SHA-256 digest, and baseline; the orchestrator reads that exact artifact with `gossip_submit` operation `candidate_page` using bounded Unicode-safe pages. The worker’s submitted report retains the same candidate reference, and the acceptance event records both the report digest and reviewed source digest. A worker cannot request full-code review for an attempt that has no source candidate. The diagram option requires all three report formats. Workers should cover task acceptance criteria and relevant classes, relationships, participants, messages, and applicable alternate, failure, retry, and authorization paths. A diagram report must contain populated sections titled **Review summary**, **Scope and evidence**, **UML class diagram**, **Sequence diagram**, **Findings**, and **Coverage and limitations**; each Mermaid block must appear in its matching section. Submission rejects missing or structurally shallow Mermaid blocks; a sequence diagram must contain at least one message between two participants, and the class diagram must connect at least two distinct classes with a relationship. Each planned coverage item must appear in the report narrative. Reviewers remain responsible for judging semantic completeness. The submitted report view has a **Download Markdown** action that saves the exact report body as a `.md` file. A worker with a live task attempt can call `gossip_task` with `operation: request_review`; the project event feed records the task, attempt, planned review type, and exact source candidate reference for the orchestrator, with an **Open attempt N** action that loads the requested attempt snapshot alongside the current task contract. Repeating the same request for an attempt does not duplicate the event. When a remote request fails because the home is unavailable, an adapter with a configured outbox persists it and retries with backoff. Source candidates and review requests retry independently; a review that arrives before its candidate waits and retries until the candidate is committed. `review_outbox` shows pending, delivered, or failed requests, `retry_review` and `discard_review` handle failed entries, and `prune_reviews` removes delivered entries. This notifies the orchestrator; it does not launch a reviewer or automatically verify submitted code or diagrams.


Project owners can prune activity history from **Settings → Retention** or with `gossip_sync` operation `prune_events` and an explicit `through_sequence`. The deletion is permanent and removes event rows only; plans, tasks, reports, messages, and queued outbound work remain. The service stores a project-local retention watermark and an audit event. A replica whose event cursor falls behind that boundary receives a reset snapshot, and its local event cache is replaced before retained events are applied. This recovers a stale cache from the current home snapshot; it does not provide peer replication or offline write authority.

For a shared local service, start `gossip coord-daemon --db /private/path/coord.db --socket /private/path/coord.sock`, then configure each agent with `gossip coord-mcp --socket /private/path/coord.sock --credential-file /private/path/agent.json` and start the dashboard with `gossip coord-ui --socket /private/path/coord.sock`. The socket parent must already exist and be private (0700 or stricter), with no symlinked ancestors; the socket is 0600. Each RPC still authenticates the project credential. The daemon refuses to replace an existing socket or file, including a stale socket after an unclean exit; inspect it before removing it. This is a local transport and does not itself provide remote federation or manage agent processes.

When a local daemon command loses its connection during project creation or enrollment, the home may have committed the operation even if the response is unavailable. CLI commands prepare credentials in a private file before mutation; retry the same command with `--resume` and the same names/role. The dashboard prepares and downloads the credential before enrollment, then can retry the same invitation; if the page is lost, use `coord-add --resume` with that file. The database stores only a token hash, so the credential cannot be reconstructed without the prepared file. Protect the socket directory as node-administrator access, since local project creation requires access to that socket rather than an existing project credential.

LAN and remote users connecting to the TLS coordination endpoint need both project-scoped gates: a CA-verified client certificate with an active grant for the project and a project credential for that project with an appropriate owner, worker, or reviewer role. FRP only forwards the TLS connection and does not change these checks. Keep client private keys and project credentials scoped to the people and machines that need them. Owners can grant or revoke certificate access in the dashboard or with `gossip_access`; changes apply immediately. Project credential revocation also applies immediately. Local Unix-socket clients use project membership credentials plus the private socket boundary. This is project admission control at the transport and application layers. The explicit project action catalog includes `project.read`, `message.send`, `task.claim`, `task.delegate`, `result.submit`, `review.decide`, `plan.edit`, `settings.edit`, `integration`, and `membership.manage`. The owner can grant `integration` separately to an integrator. `gossip_integration` records a clean observed combined commit, distinct same-repository candidate reports, and check evidence for that exact commit; Gossip labels these checks host-reported because it does not run Git merges or test commands. Integration evidence is project-readable and bound to an active integration-task attempt. To queue the integration record while disconnected, use `gossip_integration` operation `enqueue`; `outbox`, `retry`, `discard`, and `prune_delivered` expose delivery state and recovery. Replays reuse the stable request ID, so a response lost after commit does not create a duplicate. The local integration queue is limited to 100 active entries and 32 MiB; failed entries require an explicit retry or discard. Worker enrollment creates one-time `project.read`, `message.send`, `task.claim`, and `result.submit` grants; reviewer enrollment creates `project.read`, `message.send`, and `review.decide`. These are persisted grants, not live role mappings: later work-role changes do not change permissions. Every action also requires `project.read`; revoking it blocks subsequent project data and action requests. Owners retain project authority implicitly. Owners grant or revoke capabilities in the selected project's Agents panel or with `gossip_permissions`. A delegated `membership.manage` holder can enroll or revoke workers and reviewers in that project, but cannot create owners, delegate permissions, or grant TLS certificate access; remote enrollment with a certificate remains owner-only. Membership and action grants apply only to their project and are independently revocable.

For human access over LAN or FRP, run `gossip coord-ui --db /private/path/coord.db --listen 0.0.0.0 --port 8444 --tls-cert /private/ui-server.crt --tls-key /private/ui-server.key --client-ca /private/human-client-ca.crt --host ui.example:8444`. Repeat `--host` for each exact browser Host value. Non-loopback binding requires HTTPS mutual TLS and an explicit host allowlist. The owner grants the client certificate to each project, and the browser user also connects a project credential; the browser session is bound to the client certificate. Project roles govern dashboard actions. The UI uses same-origin HTTPS protections and secure session cookies. FRP can forward TCP to this listener; it does not replace TLS, certificate enrollment, or project authorization. Removing a grant through the UI or `gossip_access` revokes that certificate's access to the project on the next request.
